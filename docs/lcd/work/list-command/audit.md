## The token grep is ambiguous here, and that is worth stating

A repo-wide grep for `AC-1 (CLI)` … `AC-6 (none)` — the literal check this audit is built on —
matches **three other work-items** as well:

- `AC-1 (CLI)`, `AC-5 (CLI)` → `crates/stidcart-cli/tests/cli.rs` (write-path-skeleton)
- `AC-2 (CLI)`, `AC-3 (CLI)` → `tests/parity.rs`, `tests/container.rs` (write-path-skeleton)
- `AC-4 (CLI)` → `tests/boot.rs` (write-path-skeleton)
- `AC-6 (none)` → `tests/read.rs` (read-path, the unterminated-directory case)

AC numbering is per work-item, so this is expected rather than a defect — but it means the bare
grep would report PASS for this slug even if it had written no tests at all. The table above is
therefore scoped to the targets this work-item actually added (`tests/list.rs` in full, and the two
`ac_6_inspect_*` tests in `tests/read.rs`), each confirmed to run and pass by name.

**The same ambiguity will recur** on every future work-item numbering from AC-1, and it grows with
each one. If the audit is meant to keep biting, the fix is a slug-qualified token
(`list-command/AC-1 (CLI)`) rather than a bare one — noted here rather than acted on, since phase 6
is verification only.
